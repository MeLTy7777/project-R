# ProjectR Hermes 本番の安定化と認証(Phase H2C-B3)

新機能ではなく、**安定化と認証**のPhaseです。Apollo・新ボス・物語イベントは作っていません。カードの効果・VFX・演出・暫定のダメージ計算は変更していません(再バランスなし)。
前提のコミット: `a18cf1b`(H2C-B2)。

## 1. 物理所持のルール(変更なし・再確認)
- デッキに入れられる最大 = `min(OwnedCopies, MaxDeckCopies)`。所持が上限を超える分(例: ストレングス15枚)は保管される。
- デッキの編集・戦闘でのカード使用・Level変更は所持枚数を変えない。Card Levelは種類ごとに共通。
- 有効なデッキはちょうど30枚。報酬IDつきの付与は一度だけ(冪等)。IDなしの付与は繰り返し加算(ショップ向け)。
- 保存は `$gameSystem._projectRCardInventory`(schema 1)。CardDeckCore は未変更。詳細は `docs/ProjectR_CardCopyOwnership_H2C_B2.md`。

## 2. 初期付与の方針の監査(方針は変更していない・承認待ち)
Hermesの初期コレクションは 一閃3 / サイコポンポス3 / ヴェイル3 / ストレングス10 / 薙ぎ払い3 / 葦笛3 / 絶5 = 30枚。

### 2.1 実際の現在の挙動 = **加算(additive)**
初回入手のとき、目標の枚数を**そのまま足す**。すでに独立して持っているコピーは減らさず、その上に加える(実コード・自動テスト・実機で確認)。

| 事前の所持 | 加算(現在) | 補充(提案・未適用) |
|---|---|---|
| ストレングス 0枚 | +10 → 10枚 | +10 → 10枚 |
| ストレングス 2枚 | +10 → **12枚** | +8 → **10枚** |
| ストレングス 10枚 | +10 → 20枚 | +0 → 10枚 |

どちらでも**デッキに入れられる枚数は上限(10)まで**で変わらない。差が出るのは保管される枚数(在庫の合計)だけ。通常の新規ゲーム(事前のコピーなし)では差はない。

### 2.2 二重付与の防止(確認済み)
- 報酬ID `hermes.ring.starter` と H2C-A の付与記録(`_projectRHermesProduction`)の両方が、2回目以降の付与を止める。
- ロード・再入手・指輪の譲渡と返却・`grantStarter({explicit:true})`・同じ報酬IDの `grantBundle` のどれでも増えない(自動テスト・実機で確認)。
- 付与記録(30枚)が確認できる旧セーブは、移行時に報酬記録が作られ、以後の取得で付与されない。

### 2.3 影響プレビュー(読み取り専用・新規)
`ProjectRHermesProductionDeck.previewStarterGrant()` / `ProjectRCardInventory.previewGrant(rewardId, {cardId: 目標枚数})`
カードごとに 現在の所持・加算の結果・補充の結果・デッキに入れられる最大・差の有無、合計(例: 加算30 / 補充28)、付与済みか、次の入手で付与されるか を返す。**所持・Core・付与記録・デッキを一切変更しない**(保存領域が無い状態でも領域を作らない)。

### 2.4 決定が必要な事項
- **D1(承認待ち)**: 加算のままにするか、補充(目標に届くまでの不足分だけ)に変更するか。変更する場合は `performGrant` の1か所と、このプレビューの `policyInEffect` を切り替える小さな変更になる。承認があるまで実装は加算のまま。

## 3. 旧カードとの共存
- 旧カード(Hermes: 高速移動 `hermes_swift_movement` / 葦笛睡眠 `hermes_reed_flute_sleep` / 認識阻害 `hermes_perception_obscure` / Hermes剣術 `hermes_sword_attack`、Apollo: 黄金の弓矢・疫病攻撃・竪琴の調べ)は、IDも所持もLevelもデッキも**そのまま**。新しいHermesの入手は新7枚だけを付与し、旧カードは付与しない・削除しない・置換しない(自動テスト・実機で確認)。
- Deck Builder上では旧カードと新カードが**別のカードとして並ぶ**。取り違えやすい対応(`ProjectRHermesProductionDeck.cardGenerations()` が一覧):
  - 認識阻害 ↔ ヴェイル(どちらも「狙われなくなる」。旧=自分・5秒・State / 新=カーソル追従・範囲内の味方)
  - 葦笛睡眠 ↔ 葦笛(名前が部分一致。旧=最大2枚・12秒 / 新=最大3枚・8秒・ダメージで起床)
  - Hermes剣術 ↔ 薙ぎ払い(どちらも近接の範囲攻撃。旧=前方の短い矩形 / 新=扇状4マス)
  - 高速移動は設計7枚に対応なし(絶は別カード)。
- 表示名の**完全な重複はない**(テストで確認)。ただし上記3組は、名前や役割が近く、プレイヤーが取り違える可能性がある。
- **将来の明示的な移行の道筋(実行していない)**: (1) 旧→新の対応表(`legacyMigrationProposal()`・表示専用)に基づき、ユーザーが対象と方針を決める。(2) 旧カードの所持・Levelを新カードの付与へ**明示的な報酬ID**つきで変換する(旧カードは残すか、ユーザーが承認したときだけ未解放にする)。(3) 旧カードを含むデッキは自動で書き換えず、無効理由を表示したまま、Deck Builderで本人が入れ替える。(4) 移行は報酬IDで一度だけ。Deck Builderへの『旧』表示の追加も、この判断と一緒に決める。

## 5. ヴェイル R4a/R4b(断続的な失敗)の調査
### 5.1 経緯
H2C-B1で `h3a_verify` が1回だけ 15/17(R4a/R4b)になり、同じコードの再実行は2回とも 17/17。症状: 発動(Q)から約6シーンフレーム後の標本で、敵が追跡を続け、`checkRange` が `true`、`_detectedEvent` が残っていた。
### 5.2 追加した診断
- `tools/mz_cdp/h3a_veil_diag.cjs`: 同じ手順を繰り返し、毎フレーム(シーンフレーム数・`Graphics.frameCount`・Qキー到着フレーム・カード消費・ヴェイルの有無/中心/残り・カーソルのok/ワールド座標・主人公の位置・`isConcealed`・敵の`_detectedEvent`・敵AIの状態と連続フレーム・移動中フラグ・秘匿の統計)を記録し、原因を分類する(A=ゲーム内の遅れ / B=進行中の移動命令 / C=サンプリングの非同期 / D=標的判定の欠陥)。`MZ_JITTER=1` でQの保持時間を回ごとに変える。
- `h3a_verify.cjs` R4: 判定条件は**変えず**、`R4pre`(Qの前にカーソルが主人公の位置に届いているかを状態で確認)と、`diag0`(失敗時に、ヴェイルの有無・カーソル・秘匿判定・キャッシュ・フレーム数を詳細に残す)を追加した。固定の待ち時間は足していない。
### 5.3 結果
- 繰り返し: 12回(保持60ms)+40回(保持43〜129msで変動)= **52回すべて問題なし**。
- 決定的な遅れ: キー到着から**1フレーム後にヴェイル発効と秘匿が成立**(40/40回で 1)、**2フレーム後に敵がidleへ**(40/40回で 2)。これは仕様どおりの順序(同じフレームの敵AIはカード発動より前に走り、`_detectedEvent` は次のフレームで外れる)。検査の標本はキー到着の16〜23フレーム後なので、この遅れ(分類A=1フレームの決定的な順序)では説明できない。
- 失敗時の状態(旧記録 `docs/evidence_h2cb1/h3a_run1_FAILED_R4a_R4b.json`)は、標本時点で秘匿が成立しておらず、後半に4フレームだけ idle になっていた。**ヴェイルが主人公を覆わない位置で発動した(カーソルが届いていない)、またはQ入力が1フレームの間に押下と解放が済んで取りこぼされた**場合と整合するが、**再現できていないため原因は確定していない**。
- 判定: **原因は未特定の断続的な事象として保持する**。標的判定の欠陥(分類D)は52回の繰り返しで観察されなかった。今後 `R4pre` と `diag0` が失敗の原因(カーソルが届いていない / ヴェイル未発効 / 秘匿判定)を自動で示す。
### 5.4 ゲームコードの変更
なし(再現できる欠陥がないため)。

## 6. 旧セーブ移行の説明(新規)
ポップアップや移行ウィザードは出さず、**Deck Builderのヘッダー3行目**(既存の領域)と詳細欄、開発者向けレポートで示す。
- 区別する4つ(`ProjectRCardInventory.summary()`):
  1. **確認済みの所持**: 付与記録(30枚)・新しいゲーム・付与APIで実際に付与された枚数。
  2. **推定の最小値**: 旧セーブの解放とデッキ内の枚数から `max(1, デッキ内の枚数)` と推定した枚数。「旧セーブから移行：N種の所持枚数は推定の最小値です（実際の過去の所持数ではありません）」と表示。移行後に実際に付与しても、推定を含む枚数は確認済みに**昇格させない**。
  3. **未知・不正なカードID**: 「定義の無いカードID：…（デッキと所持の記録はそのまま保存しています）」。
  4. **無効なデッキ**: 理由は既存のヘッダー2行目(指輪ごとにまとめた説明)に出る。`summary().deckProblems` は 枚数 / 所持 / 指輪 / コピー上限 / 不明カード の件数を分けて返す(指輪の譲渡による無効は所持の問題として数えない)。
  - 未解放のままデッキにあるカード: 「未解放のままデッキにあるカード：…（解放はされません。デッキも変えていません）」。
- 新しいゲーム(旧セーブ由来でない)では説明は出ない。複数あるときは先頭の1文+「ほかN件」。
- 開発者向け: `ProjectRCardInventory.report()`(カード別の 所持/デッキ/上限/最大/区分/根拠、診断、報酬記録)と `diagnostics()`。いずれも読み取り専用。
- 旧カードの自動付与・旧エントリの削除は行わない。
